- 较新论文：3
- 经典流行开源项目：2

# 自动化边界：不处理勾选队列

勾选动作由专用 skill 单独触发。本自动化不得扫描最近日报以寻找勾选项，不执行深读、深入调研、收录到 papers/、生成或构建 learning/ unit、忽略等动作，不写 radar-processed 回执，也不修改既有日报、papers/、learning/ 或忽略清单。论文与深度文章仍须生成动作复选框，供用户后续用专用 skill 处理。开源项目只供阅读，不得生成 `#### 操作` 标题或任何动作复选框。

# 核心原则：聚焦 AI 研究与 Agent 工具

这是面向 AI 研究、AI 工程与 agent 实践的高信噪比雷达。现有 vault 仅用于去重，不决定主题范围。

- 论文和优质博客必须直接讨论 AI/ML、生成模型、推理、训练、数据、评测、对齐/安全、AI 应用或 agent；无直接 AI 关联的系统、语言、数据库、安全、硬件文章不入选。
- 开源项目必须直接帮助构建、运行、评测、观测、保护或高效使用 agent；优先框架、SDK、runtime、tool use、computer use、coding agent、agent eval、memory/context、sandbox、guardrails、agent observability，以及适合 agent 工作流的本地模型/工具。
- 不把“提到 AI”当作关联。营销包装、通用脚手架、提示词集合、账号/配额绕行、无可核验实现的仓库不入选。
- 每日结果仍应覆盖不同 AI 子方向，避免全是同一种 agent 编排或同一厂商发布。
- “与当前 vault 的关系”不参与筛选；只有明确且有帮助时才写“可能关联”。

# 生成今日日报

新鲜论文与新鲜开源项目优先检索最近 36 小时，少量低频来源可在近期出现重要更新时纳入。经典或行业验证论文、经典流行开源项目不受 36 小时限制，应从长期引用、标准基线、成熟实现、稳定维护和真实行业采用中选择。质量不足时允许少收，不凑数。

## AI 关注范围

候选范围包括但不限于：

- 基础模型、后训练、推理优化、数据、multimodal、视觉、语音、机器人和科学智能。
- Agent：规划与执行、tool use、computer use、coding agents、长期记忆、上下文管理、多 agent 协作、环境与 sandbox。
- 评测与可靠性：benchmark、verifier、agent trajectory、LLM-as-judge、对齐、安全、红队、可观测性和成本/延迟分析。
- AI 工程：模型服务、RAG/检索、agent runtime、工作流、SDK、开发者工具与本地优先的 AI 工具。

不纳入：与 AI 或 agent 使用没有直接关系的一般编程语言、操作系统、数据库、网络、安全、硬件、消费软件和开源项目。

## 论文与深度文章筛选

每天按“经典或行业验证论文”和“较新论文”两个配额选取，默认共 6 条：3 篇经典或经过行业实践验证的论文，3 篇较新论文。经典项优先覆盖理解当天新论文所需的前置概念、奠基方法或可靠基线；两类条目共同覆盖不同 AI 子方向。先通过“直接 AI 相关”资格门槛，再评分；不满足门槛不因工程质量而入选。

### 经典或行业验证论文

经典项不能只凭年代或引用量入选，至少满足以下两项：

- 已成为常用方法、标准 baseline 或后续工作的共同起点。
- 有稳定开源实现、复现结果或多项后续工作验证。
- 已在真实产品、研究流程或行业系统中长期使用，并有一手证据。
- 方法边界清晰，今天仍能帮助理解或实践相关方向。

每条经典项须说明“前置价值”和“实际检验信号”，能与当天某篇较新论文形成理解链时明确指出。

### 较新论文

较新项强调近期研究增量，优先最近 36 小时；低频来源、周末或没有足够高质量候选时，可放宽到最近 7 天并标明日期。每条须说明依赖的前置概念；若与当天经典项相关，明确指出对应关系。

#### 来源与质量门槛

- arXiv RSS 可作为较新论文的主要发现与全文入口；对每个 arXiv 候选，必须继续核验官方 proceedings、期刊页面或 OpenReview 的正式录用决定，以确认 venue 与质量状态。优先覆盖 NeurIPS、ICLR、ICML、ACL/EMNLP/NAACL、CVPR/ICCV/ECCV、AAAI/IJCAI、MLSys、AISTATS、RSS、CoRL、TMLR、JMLR、TPAMI 等与 AI/agent 直接相关的 venue。聚合页只能发现候选，最终至少回链 arXiv/论文全文，并在有录用或发表状态时同时回链相应官方页面。
- 每条按事实标明时间状态：`近期发表`（官方公开日期）、`近期录用`（官方决定日期）或 `较早录用、近期公开`。录用日期与公开日期相隔较久时，不能把它写成新论文；若为近期录用但论文尚未公开，应只在能访问官方摘要/稿件时纳入。
- 有近期 arXiv 版本且能核验官方录用/发表状态的论文，可同时满足时效与质量要求，应优先入选。无法确认 venue 状态的近期 arXiv 预印本仍可补充，但须至少具备一项可核验强证据：公开代码或数据、可复现实验与充分 baseline、明确实验设置/局限，或来自一手研究机构并提供技术细节。仅有摘要、营销叙述或缺乏方法证据的预印本不入选。
- 具官方 venue 证据的候选和强证据预印本仍不足时允许少收，不得以普通预印本凑满较新论文配额。

评分：

- 内容本身的重要性与长期价值：30%
- 技术深度、证据和可验证性：30%
- 新颖性与信息增量：20%
- 可复用方法或实践价值：20%

当前 vault 相关性不计分，不得作为入选门槛。厂商数字标明“厂商自报”；论文要检查实验、baseline、代码/数据和局限；独立文章要核验技术事实和原始引用。

## 开源项目筛选

每天按“经典流行开源项目”和“新鲜开源项目”两个配额选取，默认共 7 个：2 个经典流行项目，5 个新鲜项目。项目必须直接属于 agent framework/SDK、agent runtime、tool use、computer use、coding agent、agent evaluation、memory/context、sandbox、guardrails、agent observability，或能显著提高本地 agent 使用体验的工具。

### 经典流行项目

经典项应有较长时间的维护记录、清晰的版本与迁移路径、广泛真实使用或行业采用证据，并且今天仍有实践价值。Stars 只能辅助说明传播度，不能单独证明成熟度。

### 新鲜项目

新鲜项优先选择最近 36 小时内在许可发现源出现、近期有实质 release 或活跃开发，或获得高质量社区关注的项目。重点说明它解决的 agent 问题、核心设计和适用场景；质量不足时允许少收。

候选发现只使用以下来源：

- GitHub Trending（daily/weekly）。
- Hacker News / Show HN。
- Lobsters。
- Product Hunt 的 AI 分类或 feed。

严禁使用 GitHub repository search、按创建时间的仓库筛选、GitHub new-repository 列表或 recent releases 作为发现渠道。官方仓库、README、release 和 issue/PR 活动只用于核验，不能倒推为发现来源。Product Hunt 上没有公开仓库、明确许可证和最小可运行说明的项目直接排除。

每次运行应检查上述四类来源中可访问的页面；最终候选集至少来自两个发现站点。单个条目可只由一个发现站点发现，官方仓库不算第二个发现站点。某来源当天没有合格开源项目时不强行纳入。

排除通用应用、与 agent 无关的开发工具、仅包装现有 API 的壳项目、账号/配额绕行工具、提示词合集、无可验证代码或文档的仓库。

对每个候选核验：

- 官方 GitHub/GitLab/Codeberg 仓库及 README。
- 清晰的问题定义、核心设计或架构。
- LICENSE 文件；没有明确许可证时必须指出。
- 最近提交或 release、是否 archived、文档和最小运行示例。
- 有条件时检查 CI、测试、issue/PR 活动和维护者背景。
- Stars 仅作为传播度背景，不得替代质量判断。
- 聚合站描述与 README 冲突时以仓库和代码为准。

项目评分：

- 问题价值与设计清晰度：25%
- 实现、文档、测试与可验证性：25%
- 活跃度和维护信号：20%
- 新颖性：15%
- 实际可用性：15%

## 去重执行门槛（强制）

- 在选择和写入日报前，必须建立当日候选清单，并对每个候选逐条执行精确去重；不得以一次宽泛搜索、部分输出或人工抽样代替。
- 论文/文章至少分别检索：裸 arXiv ID（如 `2310.06770`）、规范化标题、规范化 URL 的 `/abs/`、`/html/`、`/src/` 变体和既有 radar-id；项目至少分别检索 `github:owner/repo`、仓库规范化 URL 与标准化项目名。
- 每个检索键必须覆盖既定全部去重范围；禁止使用 `head`、`tail`、截断输出或只匹配单一 URL 变体作为去重结论。
- 任一键命中即视为重复，候选必须在写日报前排除；不得以“经典项配额”或主题关联保留。运行报告只记录跳过原因，不写入日报正文。
- 写入前再次对最终入选清单逐条运行同一检查，并在结束验证中确认所有候选均为零命中；若检查失败、输出截断或范围不可读，宁可少收，不得写入该候选。

## 日报叙事与 Markdown 写作（强制）

- 日报是供人连续阅读的研究简报，不得写成字段清单或“每句一个 bullet”的资料卡。每个主要模块先用 1–2 个主体段落说明本节的共同信号、判断和取舍。
- “论文与深度文章”按 `### 经典或行业验证论文`、`### 较新论文` 分组；“开源项目”按 `### 经典流行项目`、`### 新鲜项目` 分组。各条目使用四级标题，并在分组标题中写出实际条目数。
- 每个条目保留标题与 radar-id；将分类、类型、作者/机构、日期、原文和阅读成本压缩为一行简洁元信息。随后用连贯段落先解释“为什么现在值得看”，再按需要拆为“方法与证据”“边界与追问”“快速理解”等小标题。
- 段落应以结论或问题开头，随后给出因果、方法、证据和限制；不要把“问题、方法、发现、证据、局限”机械拆成五个单句列表。事实需要并列扫描时才使用短列表。
- 允许、也应在解释复杂机制、评测协议、比较框架或行动路径时使用有意义的五级标题，形成叙事层次。论文与深度文章的动作复选框、真正并列的验证项目和简短映射可以使用列表；开源项目不得包含动作复选框。
- 若当天文件已存在，必须保留已有隐藏注释、论文与深度文章的动作复选框、可见/隐藏处理回执和用户已补写的内容；不得清除已勾选状态或改变其语义。开源项目不继续生成旧版动作区；若旧版动作区已有勾选或用户补写内容，先把有效信息并入相邻正文，再移除动作区。
- 开源项目保留一行简洁元信息，并用一个短段落交代它解决的问题、核心设计和适用场景；不创建“成熟度与风险”或其他风险分析小节。

## 文本可读性审阅（强制）

- 完成研究和去重后、用 apply_patch 写入日报前，调用 `$shuorenhua` 对将要写入的正文做可读性审阅；主场景为 `docs`，默认 `standard`，文本已清楚且仅有局部模板感时降为 `minimal`。
- 审阅范围仅限“今日视野”和条目的解释性正文。不得改动 frontmatter、标题层级、`radar-id`、作者/机构、日期、数字、单位、公式、模型/数据集/benchmark 名称、链接与引用、代码、复选框、隐藏注释、处理回执和用户补写内容；这些均按 protected spans 原样保留。
- 对当天新建日报，可在事实不变的前提下做有限的段落、句序和句长调整；更新已有日报时，只处理自动化生成的正文，并采用 `in-place` 或等价的保守处理，不删除整句、不合并段落、不改变用户内容或既有动作语义。
- 改写应删去开场套话、空泛总结、narrator 腔、商业黑话、虚假二元对比和无证据拔高，直接说明问题、方法、证据、限制与适用条件。不得新增事实、来源、判断或责任主体，不得删去核心限制，也不得将技术说明写成口语化或营销文案；无来源断言按 `docs` 的 `audit-only` 原则处理。
- 写入前必须完成两次回读：先核对事实、术语、责任主体、链接、数字、引用和语义均未漂移，再检查开场套话、空收尾、narrator 腔、空泛判断和句长过匀等残留。若可读性改动会损害保真、术语稳定或正式度，保留原文。

# 安全边界

- 本自动化只创建或更新当天的 inbox/知识科技雷达/ 日报；不处理历史队列。
- 不修改 papers/、learning/、忽略清单、.obsidian/、其他 inbox 目录或无关文件，不创建 publish/。

- 不向外部服务发送私有 vault 内容。
- 运行结束报告日报路径、经典或行业验证论文数、较新论文数、经典流行项目数、新鲜项目数、主要发现渠道和格式检查状态；跳过原因只在运行报告中说明。

# 运行可靠性（强制）

- 此自动化运行在干净的本地 shell，不能假定 $CODEX_HOME 已设置。运行前将记忆目录解析为 `${CODEX_HOME:-$HOME/.codex}/automations/automation`，记忆文件为该目录下的 `memory.md`。
- 先读取该记忆文件（若存在），并在结束前写入本轮的简短摘要与运行时间。创建或写入记忆失败时，记录原因，但不得阻塞日报生成。
- 在研究完成后，先用 apply_patch 写入 inbox/知识科技雷达/YYYY-MM-DD.md，再写运行记忆。结束前验证日报文件存在、三个主要模块齐全、四个可调分类的条目数分别符合配额或已明确说明少收原因、开源项目中不存在 `#### 操作`/`操作：`/动作复选框，并运行空白/格式检查。
