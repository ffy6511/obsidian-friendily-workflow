# 分层与栏位

和**同一品类里已经有的实现**比，不要和「没有这件事的产品」从 0 比。评测产品就跟别的评测比。

分层决定**放进这篇的哪一栏**，不是决定「有没有做」，也不是「全文只准写超出预期」。

## 三层

| 层 | 是什么 | 放哪 |
| --- | --- | --- |
| **默认需求** | 用户心里默认你已经做了的。品类地板，或软件工程里不被拿来吹的能力。 | **不要放进特点 / 亮点栏。** 绝大多时候也不用单独成章。真要交代，丢进问答或编写说明，或删掉。 |
| **基本功能** | 这产品确实要有、读者也要能找到，但同类大多也有。 | **正文、怎么用、快速开始、参考。** 不占特点栏，不当口号反复念。 |
| **超出预期** | 相对同类做法不同，比较结果会变，而且真的有用。 | **特点 / 亮点栏**（这篇如果有这一栏）。标题要能说出比谁、便宜在哪 / 快在哪 / 复用的是什么。 |

测试超出预期：拿掉这句话，和同类比，读者是否还觉得有理由专门用你。测不过，就不是特点栏的料。

机制本身（「我们有插件」「我们有打分」）通常是默认需求或基本功能。只有相对同类真正便宜 / 快 / 可复用的那一层，才进特点栏。

## 对栏

先画出这篇**实际有的栏**（介绍、怎么用、特点、正文、FAQ、参考……），再把主张放进去。不要假设每篇都有三张特点卡。

没有单独特点栏的文档（教程、API、内部设计）：仍按三层决定详略。默认需求不要写成章节主角；基本功能按读者需要写进正文；真正不同的做法才值得提前或加粗。

删掉信息密度低的堆积：同一句念四遍、报能力菜单、把卫生项当明星章节。
